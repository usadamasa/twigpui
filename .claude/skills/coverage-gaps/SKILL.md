# coverage-gaps

## 測る

```sh
scripts/coverage.sh              # per-file の表 (markdown)
scripts/coverage.sh --gaps src/x_api    # 呼ばれていない関数を file:line + ソース行で
scripts/coverage.sh --json       # 同じ数字を JSON で
```

**2 回目からは速い。** `src` に何も触っていなければ 1 秒未満で返る。
プロファイルより新しいファイルがあるときだけ測り直す (1〜2 分) ので、
表を見る → 穴を出す → テストを書く → 測り直す、のループで払うビルドは
**テストを書いた 1 回ぶんだけ**。

`COVERAGE_REUSE=1` を付けると古くても再利用する。CI が同じプロファイルから
複数のレポートを出すのに使っているだけで、**手元では使わないこと。**
編集した後に付けると、直す前のコードの数字が返る。

CI では Coverage ジョブが同じものを step summary に貼る。**必須チェックではない。**
落ちても止まらないし、そもそも閾値が無い。

## 数字が「実装だけ」である理由

`cargo llvm-cov` は自分がコンパイルしたものを全部計測する。このリポジトリは
テストを実装と同じファイルの `#[cfg(test)]` に置いているので、**テスト関数が
テスト自身をカバーしている**。

| | regions |
| --- | ---: |
| `cargo llvm-cov` が出す数字 | 79.20% |
| 実装だけ (`#[cfg(test)]` より前) | **53.74%** |

25 ポイント以上ちがう (2026-08-24 実測、1880 関数中 1077 がテスト関数)。
`scripts/coverage.sh` は `code-metrics.sh` と同じ `#[cfg(test)]` の境界で切って
実装側だけを数える。**素の `cargo llvm-cov` の出力を読んで判断しないこと。**

既製ツールにこの分離は無い。cargo-llvm-cov の issue #123
(Ignore all `#[test]`-related code automatically) は open のままで、除外は
ファイル単位か package 単位しかない。`#[coverage(off)]` 属性は nightly 限定。

## 埋める価値のある穴を選ぶ

**カバレッジは地図であって目標ではない。** 数字を上げるためのテストは書かない。
穴を見つけたら、まず次のどれに当たるかを判断する。

### 埋められる — テストを書く

| 穴 | 書き方 |
| --- | --- |
| 純粋関数、パース、フォーマット、状態遷移 | 通常の `#[test]` |
| 要素の間隔・位置・寸法 | `debug_bounds` (#184) |
| クリックが要素に当たるか | `simulate_click` + `debug_bounds` (#184) |
| キーバインド・action の配線 | `dispatch_action` (#146 層 3) |
| エラーパス (`could not write …` など) | 失敗する入力を作って通す |

**寸法とクリックは書ける。** #146 の本文が長らく「テストプラットフォームは
レイアウトを走らせない」と書いていたのは誤りで、#184 で否定された。
`fixture-visual-check` スキルに現在の切り分けがある。

### 埋められない — 穴のままでよい

| 穴 | 理由 |
| --- | --- |
| メニューの登録 | `TestPlatform::set_menus` が no-op (#115 理由 1) |
| 色・フォント・字の詰まり方 | `TestWindow::draw` が no-op。`Scene` から先は走らない (#115 理由 2) |
| 実 API を叩くコード | テストはネットワークを叩かない。`x-api-budget` |

`x_api/client/mod.rs` (transport) と `client/endpoints.rs` のカバレッジが低いのは
**正しい状態**。ここを上げようとして
ネットワークを叩くテストを書いてはいけない。埋めるならフィクスチャ JSON を
使ったパースとエラー変換のテストで、それは既に厚い (`x_api/model.rs` は 99%)。

### 判断に迷ったら

「この関数が壊れたとき、テストで気づけるべきか」を問う。
気づけるべきなら書く。気づきようがない (画面を見るしかない) なら #115 へ。

## 手順

1. `scripts/coverage.sh` で全体を見て、低いファイルを 1 つ選ぶ
2. `scripts/coverage.sh --gaps src/選んだファイル` で呼ばれていない関数を出す
3. 上の表でどれに当たるか仕分ける
4. 埋められるものを TDD で書く (`test-driven-development` スキル)。
   **先にテストを書いて落ちることを確かめる。** 通ってしまうテストは何も守らない
5. `scripts/coverage.sh --gaps src/選んだファイル` をもう一度。テストを書いた
   ぶん測り直しが入り、狙った関数が一覧から消えていれば閉じている
6. 埋められないものが残ったら、それが #115 に載っているか見る。
   載っていないなら足す (理由を明記して)

## やらないこと

- **数字のためのテスト。** getter を呼ぶだけ、`Debug` を実行するだけのテストは
  カバレッジを上げて何も守らない。レビューで落ちる
- **閾値の導入。** `metrics-baseline.tsv` の理由がそのまま当てはまる。初日から
  落ちるチェックは無効化される。加えてカバレッジには固有の問題があり、
  テストの書けない描画コードを足した PR が理由なく数字を下げる
- **カバレッジを理由にした課金。** 実 API を叩くテストは、どれだけ穴が埋まっても
  書かない
