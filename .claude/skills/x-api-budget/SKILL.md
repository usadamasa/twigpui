# x-api-budget

X API はプリペイド残高からの従量課金で、リクエストを 1 本足すことが直接お金になる。
このリポジトリで API 呼び出しに触るときは、機能の前にまず請求を数える。

## 1 操作あたりのリクエスト数

| 操作 | 消費 | 内訳 |
| --- | --- | --- |
| 起動・リロード | 2 | ID 解決 (`GET /2/users/me`) + タイムライン取得 |
| 「Load older」1 クリック | 1 | `meta.next_token` を辿る追加取得 |
| `--fetch-only` | 2 | screen name 検索 + `GET /2/users/:id/tweets` |
| 「Show thread」1 クリック | 最大 5 | 親を 1 階層ずつ `GET /2/tweets?ids=`。前の階層が解決するまで次の id が分からないのでバッチできない |

リポスト・引用・返信先の展開は `expansions` に相乗りするので**追加コストがゼロ**。
同じレスポンスの `includes` から join する設計を崩さない。

## 新しい呼び出しを足すときの規則

- **ポーリングや自動更新を足すなら、取得間隔とキャッシュを必ずセットで設計する。**
  間隔だけ決めてキャッシュを後回しにすると、そのまま課金が線形に増える。
- 複数 id を引くときは `GET /2/tweets?ids=` にカンマ区切りでまとめる。
  X 側のクエリパラメータが複数 id を受けるので、何件でも 1 リクエストで済む。
- ユーザーのクリック 1 回で複数リクエストが飛ぶなら、**押す前に最悪ケースを UI に出す**
  (「Show thread (up to 5 requests)」がその形)。

## 残高が尽きたとき

`429` が返り、本文が `UsageCapExceeded` になる。レートリミットの `429` とは別物で、
待っても回復しない。エラー変換はこの 2 つを取り違えないこと。

## キャッシュとレートリミットの分離

ホームタイムラインと単一ユーザーのタイムラインは、**同じ user id でも中身が違う**。

- キャッシュは `Paths::home_timeline_file` と `Paths::timeline_file` に分けてある。
  片方に寄せると、表示中のタイムラインが別モードの結果で上書きされる。
- レートリミットは `/users/me` とホームタイムラインを**それぞれ独立した `Endpoint`** として
  追跡する。エンドポイントを足したら `Endpoint` も足す。

`--fetch-post` はタイムラインキャッシュを読まないし書かない。
任意の post id は「一度引かれるだけ」のアクセスパターンで、
同じアカウントのタイムラインを繰り返し引くのとは性質が違うため。

## 認証は 1 種類しかない

資格情報は OAuth 2.0 Authorization Code (ユーザーコンテキスト) だけ。
アプリ専用 Bearer トークンは廃止済みで、資格情報の種類で表示先を分岐させる仕組みは無い。

`GET /2/users/:id/timelines/reverse_chronological` はユーザーコンテキスト必須。
`GET /2/users/:id/tweets` は OAuth トークンでも普通に叩ける。

## テスト

**テストはネットワークを叩かない。** パースとエラー変換をフィクスチャ JSON で検証する。
テストが課金を発生させないことを保ちつづける。
