# x-api-budget

X API はプリペイド残高からの従量課金。このリポジトリで API 呼び出しに触るときは、
機能の前にまず請求を数える。

ここには判断の規範だけ置く。詳細は 2 つの reference に分けてある。

- `reference/pricing.md` — **X 側の課金仕様**。単価表、出典と更新の仕方、
  dedup と月次上限の原文、`GET /2/usage/tweets` の叩き方、実測ログ
- `reference/app-behavior.md` — **twigpui 側の挙動**。1 操作あたりのリクエスト数、
  レートリミットの追従、消費集計 (`usage.json`)、ローカルキャッシュ

エンドポイントの契約と実挙動 (どの scope で何が届くか、パラメータの綴り、4xx の読み方)
は `x-api-endpoints` が担当する。

## 最初に読むべき一行

**課金の単位はリクエストではなく resource。読み取りは「返ってきた件数」で課金される。**

2026-08-23 の実測。`GET /2/lists/:id/tweets?max_results=100` を **1 本**撃ったら、
project の日次カウンタが 20 から 119 へ動いた。返却は 98 件。

だから `max_results` は表示の設定ではなく**支出の設定**。20 から 100 に上げることは、
1 回の取得の値段を 5 倍にすることと同じ。取得件数に触るときは必ずここに戻る。

書き込み (投稿・いいね・リポスト・削除) はリクエスト単位のまま。

## 数え方の規範

- **同じ resource は UTC の 1 日で 1 回しか課金されない。**
  リロードを連打しても増えるのは新着の分だけ。ただし日をまたげば同じ post に再び課金される。
  ローカルキャッシュが効いているのはそっちの側で、dedup の代わりにはならない。
- **`includes` の中身を「タダ」と書かない。** リポストの元投稿 (`includes.tweets`) が
  Post として課金されていないことは実測済み。**`includes.users` は未解決**で、
  `GET /2/usage/tweets` では測れない (Post 専用のカウンタのため)。
- **自分のデータは他人の投稿の 5 分の 1** (Owned Reads)。用途を自分のアカウント側へ
  寄せると桁が変わる。

## 1 操作あたりの見込み

`max_results` の既定は 20 (`X_MAX_RESULTS`)。同日 dedup があるので、
下の resource 数は**すべて新着だった場合の上限**。

| 操作 | リクエスト | resource (上限) |
| --- | --- | --- |
| 起動・リロード | 2 | Users 1 (`/users/me`、30 日キャッシュで通常 0) + Posts 20 |
| 「Load older」1 クリック | 1 | Posts 20 |
| `--fetch-only` | 2 | Users 1 + Posts (Owned Reads) 20 |
| 「Show thread」1 クリック | 最大 5 | Posts 最大 5 |
| 自動更新 1 ポーリング (#21) | 1 | Posts 20 (同日 dedup 後は新着分のみ) |
| 「N new posts」バーを押す | 0 | 0 |
| ステータスバーから手動同期 (#174) | フォロー数と List 件数に比例 | Users 両側の全件 |

`GET /2/tweets?ids=` は 1 リクエストで 100 件まで束ねられるが、**課金は件数のまま**。
まとめて減るのはリクエスト本数と待ち時間であって、請求ではない。

### 自動更新 (#21) の課金の読み方

既定は 3 分間隔 (`X_AUTO_REFRESH_INTERVAL_SECONDS`。#22 の stick-to-top follow で
5 分から詰めた)。**リクエスト本数だけ見ると 1 日 480 本**で多く見えるが、
resource で数えると話が変わる。

`GET /2/lists/:id/tweets` は `since_id` を取らないので、ポーリングは毎回先頭ページを
読み直す。表の 20 はその上限であって実額ではない。同日 dedup が効くため、
**定常状態で課金されるのはその日に実際に増えた post だけ**。読む以上どのみち払う分で、
間隔を詰めても総額はほぼ動かない (増えるのはリクエスト本数とレートリミットの消費)。

繰り返し課金されるのは **UTC 日付が変わった直後の 1 ページ** (上限 `max_results`)。
1 日 1 回、20 resource 程度。

したがって `auto_refresh_interval_seconds` は**支出のつまみではなく応答性のつまみ**。
支出のつまみは `max_results` のまま (「最初に読むべき一行」を参照)。
ただしこれは dedup が Posts に効くという実測に全面的に乗っている。
dedup の前提が崩れたらこの段落ごと書き直すこと。

`X_AUTO_REFRESH=false` でループ自体が起動しない。切れば自動更新の課金はゼロになる。

### 手動同期 (#174) はこのアプリで一番高いクリック

ステータスバーの「List sync:」を押すと同期が始まる。**diff は両側を全件読む**ので、
フォロー数千件なら 1 クリックでドル単位。表の「リクエスト」が数字でないのはそのためで、
ページングが伸びる分だけ本数も resource も増える。

だから 2 段クリックにしてある (`x-api-budget` の「押す前に最悪ケースを UI に出す」)。
1 クリック目で課金の内容を出し、2 クリック目で初めて撃つ。

**間隔だけを外す。** 手動起動は `sync_interval_seconds` を無視するが、
レートリミットと「未消化の plan があればそれを先に流す」順序はそのまま
(`schedule::next_step` の precedence を触っていない)。
つまり catch-up の途中で押しても読み直しは走らず、支払い済みの plan の続きになる。
読みを買い直すのは plan が空のときだけ。

**tick が走っている間は押せない。** `SyncStatus::Working` の間クリックを拒否する。
task slot を差し替えても実行中の tick は止まらない (background thread で同期実行される) ので、
拒否しないと両側の全件読みを二重に買う。

## 新しい呼び出しを足すときの規則

- **ポーリングや自動更新を足すなら、取得間隔とキャッシュを必ずセットで設計する。**
  間隔だけ決めてキャッシュを後回しにすると、そのまま課金が線形に増える。
- **件数が可変なら先に最悪ケースを数える。** フォロー一覧の全件取得のように
  ページングが伸びるものは、resource 数がそのまま請求になる。
- ユーザーのクリック 1 回で複数リクエストが飛ぶなら、**押す前に最悪ケースを UI に出す**
  (「Show thread (up to 5 requests)」がその形)。件数で課金される以上、
  この表示も本来はリクエスト数ではなく件数で出すべき。

## アプリの消費集計は今まちがっている

`src/usage.rs` は**リクエスト本数**を数えている。実際の課金は resource 単位なので、
表示されている数字は実態と 1 桁から 2 桁ずれる。#162 で直す。
それまでは「何回呼びに行ったか」であって「いくらかかったか」ではない。

正しい消費を見る手段は 2 つ。手順は `reference/pricing.md`。

1. Developer Console の Usage / Billing の明細 (金額が見える唯一の場所)
2. `GET /2/usage/tweets` (Post 消費のみ。app-only Bearer 必須)

## 残高が尽きたとき

`429` が返り、本文が `UsageCapExceeded` になる。レートリミットの `429` とは別物で、
待っても回復しない。エラー変換はこの 2 つを取り違えないこと。

## キャッシュとレートリミットの分離

ホームタイムラインと単一ユーザーのタイムラインは、**同じ user id でも中身が違う**。

- キャッシュは `Paths::home_timeline_file` と `Paths::timeline_file` に分けてある。
  片方に寄せると、表示中のタイムラインが別モードの結果で上書きされる。
- レートリミットは `/users/me` とホームタイムラインを**それぞれ独立した `Endpoint`** として
  追跡する。エンドポイントを足したら `Endpoint` も足す。

`--fetch-post` はタイムラインキャッシュを読まないし書かない。
任意の post id は「一度引かれるだけ」のアクセスパターンで、
同じアカウントのタイムラインを繰り返し引くのとは性質が違うため。

## アプリの資格情報は 1 種類

アプリが使うのは OAuth 2.0 Authorization Code (ユーザーコンテキスト) だけ。
アプリ専用 Bearer トークンは #33 で廃止した。

例外は `GET /2/usage/tweets` で、これだけは app-only Bearer でしか叩けない。
アプリの経路ではなく、計測のための別経路として扱う。

## テスト

**テストはネットワークを叩かない。** パースとエラー変換をフィクスチャ JSON で検証する。
テストが課金を発生させないことを保ちつづける。
