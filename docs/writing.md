# 書き込み: 投稿・返信・引用・repost・like・削除

このアプリが X へ送り返せるものすべて｡操作ごとのコストは
[API budget](../.claude/skills/x-api-budget/reference/app-behavior.md) を参照｡

## 投稿

OAuth でサインインし､上の "Scopes" の注記に従って再認可すると､ヘッダーの
下にコンポーザーが現れる: 下書き領域､`weighted/280` の文字数カウンター､
"Post" ボタンだ｡送信すると `POST /2/tweets` を呼ぶ｡成功すれば下書きを
クリアして通常のリロードへ落ちる (他のリロードと同じく下記の取得間隔に
従う) ので､新しい post が現れる｡失敗したとき — ネットワークエラー､
レートリミット､文字数制限､スコープ不足 — は下書きを打ったそのままで
残す｡リクエストの失敗で書いたものを失う道は無い｡

**入力 (#38)｡** 下書き領域は､twigpui が生のキーイベントを自分で読むのでは
なく､[`gpui-component`](https://crates.io/crates/gpui-component) crate の
本物のテキスト入力ウィジェット (`gpui_component::input::Input`､裏は
`InputState` で､gpui の `EntityInputHandler` をきちんと実装している) だ｡
IME による変換 — 日本語・中国語・韓国語､その他どの入力メソッドでも —
が動作し､カーソル移動・テキスト選択・コピー/ペースト/undo/redo も効く｡
ボックスは固定高をスクロールするのではなく､下書きに合わせて伸びる
(2〜8 行)｡それでもこれは素のテキストコンポーザーであってフルクライアント
ではない: @mention/#hashtag の補完もメディアの添付も無く､Enter は送信では
なく改行を挿入する — 送信するのは "Post" ボタンだけだ｡

**文字数のカウント｡** X の 280 文字制限は､何かを送る前にクライアント側で､
X 自身の "weighted length" のルール (オープンソースの `twitter-text`
ライブラリに従う) を使って強制する｡`http://`/`https://` のトークンは実際の
長さにかかわらず一律 23 として数え (X 自身のリンク短縮に合わせている)､
コードポイントは "low weight" の範囲の短いリスト (素の ASCII､Latin-1､
残りの Latin Extended/ギリシャ文字/キリル文字､いくつかの約物の範囲) に
入れば 1､そうでなければ 2 として数える — CJK 統合漢字､ハングル､
ひらがな/カタカナ (全角も半角も)､全角形､絵文字､そして low-weight の
リストに無いその他すべてだ (#61)｡

**二重送信｡** 送信ボタンは､投稿できるものがあって､かつ送信中のものが無い
ときだけそもそもクリックできる｡クリックすると､ネットワーク呼び出しが
始まる前に同期的にコンポーザーを "Submitting" にするので､最初のリクエストが
解決する前の 2 回目のクリックには何もすることが無い｡

**レートリミット｡** `POST /2/tweets` は独自のエンドポイントとして追跡する
(#10) — 下の "Rate limits" を参照｡

## post を引用する

ほとんどの post は本文の横に "Quote" のアクションを出す — 唯一の例外は下の
「ボタンが付かない post」を参照｡クリックしただけでは何も送らない｡その post を
引用対象としてコンポーザーに読み込み､下書き領域の下に枠付きのカードとして
描画する — #13 が timeline で引用を見せるのにすでに使っているのと同じカードだ
(上の "Status" の「repost と引用は展開する」を参照)｡そこから入力して送信
するのは､普通の post とまったく同じに動く — 同じ文字数カウンター､同じ
二重送信のガード､同じ「失敗しても下書きを決して失わない」保証 — ただし
リクエストが `quote_tweet_id` も運ぶ点が違う｡引用専用のエンドポイントは
無い｡`POST /2/tweets` は省略可能な `quote_tweet_id` を受け付けるので､引用は
素の post で `POST /2/tweets` がすでに送っているのと同じリクエスト (上の
#14 を参照) と､同じ `Endpoint::CreatePost` のレートリミット追跡 (#10) を
使い回す — 専用の引用エンドポイントを設けても､その追跡を誤って分割する
だけになる｡X 自身がこれを 1 つのエンドポイントとして扱っているからだ｡
引用を伴わない post はこのフィールドを一切送らない (`null` としてすら
送らない) — 実際に引用している post だけがこれを運ぶ｡

**引用の取り消し｡** カードの隣に "Remove quote" が現れ､下書きのテキストは
触らずに引用対象だけを消す — "Quote" の押し間違いで､すでに打ってあった
ものを捨てさせられることはない｡下書きは普通の post に戻り､そこから送信
すると `quote_tweet_id` は一切送られない｡

**自分の post を引用してもよい｡** repost (#15､下記) と違って､X の API は
自分の post を引用することを拒否しないので､twigpui もクライアント側で
確認しない｡

**repost の行を引用すると元の post を引用する** (#52) — それは引用カードが
見せることになるテキストと著者でもある｡行が描画しているのがそれだからだ｡

## 自分の post を削除する

自分の post には "Delete" のアクションが出る｡他人の post には出ない｡X が
他人の post の削除を拒否するので､失敗することしかできないリクエストに金を
使う意味が無いからだ｡

**削除は必ず 2 クリックで､1 クリックでは起きない｡** "Delete" は自分自身を
"Delete permanently" / "Cancel" に置き換える｡この操作は取り消せないので､
1 回のクリックで post を壊せる道は無い｡問いかけを出せる行は一度に 1 つだけ
だ — 別のところで "Delete" をクリックすると､2 つ目が開くのではなく問いかけが
そちらへ移る｡

**キャッシュからも消える｡** X からは削除されたのに `timeline-<id>.json` に
残っている post は､ウィンドウからは消えて次の起動で戻ってくる — 動いて
いないのに動いたように見える状態だ｡そこで削除に成功したら､キャッシュ
ファイルを書き直したうえで**読み直し**､書いたばかりのものではなく実際に
ディスクにあるものを描画する｡ローカルキャッシュに触るのは X が削除を確認した
後だけだ｡先に忘れてしまうと､まだ存在する post を隠すことになる｡

**repost の行に Delete は付かない｡** #52 以降の他のすべてのアクションとは
違う｡そういう行は誰かの元の post を表示しているので､*自分の* post の repost
では､「自分の repost」と読める行から元の post を破壊することになる｡repost を
取り消すのは repost トグルの仕事 (#15) であり､取り消せない操作でこの 2 つを
混同するのは､リスクに見合わない｡

`DELETE /2/tweets/:id`､`tweet.write` スコープ､1 リクエスト｡他のすべての
書き込みと同じく spend として数える｡

## 返信する

どの post にも "Reply" のアクションが出る｡クリックするとコンポーザーの
対象を設定するだけで他には何もしない — "Quote" と同じで､下書きを送信する
まではリクエストが出ない｡コンポーザーは答える相手の post のカードの上に
"Replying to @someone" を表示し､すでに打ってあったものを失わずに消せる
"Remove reply" を添える｡送信は普通の post と同じ `POST /2/tweets` を送り､
そこに `reply.in_reply_to_tweet_id` をネストする｡スコープ (`tweet.write`)
もコスト (1 リクエスト) も同一だ｡

**下書きは返信か引用のどちらかで､両方にはならない｡** X の API は両方を
兼ねたものも受け付けるが､このコンポーザーはそれを組み立てるのを拒む｡
小さなコンポーザーの中では両者はほとんど同じに見えるうえ､間違ったほうを
送っても目に見える失敗にならない — 返信は会話の下にぶら下がるが､引用は
そうならない｡だから引用を設定したまま "Reply" をクリックするのは追加では
なく切り替えであり､どちらに転んでも下書きのテキストは残る｡

**repost の行から返信すると元の post に答える** (#52) — `in_reply_to_tweet_id`
として送る id は retweet のアクティビティのものではなく元の post のものだ｡
ここを間違えると返信をまったく別の会話にぶら下げてしまい､しかもその失敗は
後から何も見えない｡

**その後に再取得するものは通常のリロード以外に無い｡** "Show thread" (#12)
が辿るのは post の*祖先*で､新しい返信は子孫なので､返信しても古くなる
キャッシュ済みの連なりは無い｡返信そのものは､成功したどの post も必ず
起こす timeline のリロードで現れる｡

## repost と repost の取り消し

自分の post 以外のすべてに "Repost" / "Reposted" のトグルが出る — 下の
「ボタンが付かない post」を参照｡"Repost" のクリックは
`POST /2/users/:id/retweets` を送り､(取り消しの) "Reposted" のクリックは
`DELETE /2/users/:id/retweets/:source_tweet_id` を送る｡ボタンはクリックで
即座に切り替わり — 楽観的更新で､何かが変わるのをネットワーク待ちしない —
リクエストが失敗したら元に戻る｡確認ダイアログは無い｡repost は取り消せる
操作で､他のどの X クライアントも事前に尋ねないのと同じだ｡

**twigpui は､ある post をすでに repost したかどうかを API 自身からは
判別できない｡** X API v2 の timeline レスポンスにこれを表すフィールドは
無い — v1.1 の `retweeted` と違って v2 に相当物が無い — し､post ごとに
`GET /2/tweets/:id/retweeted_by` で確かめると表示中の post 1 件につき
1 リクエストかかる｡キャッシュのすべてが spend を避けるために存在する
アプリには論外だ｡そこで twigpui は代わりに自前のローカルな記録を持つ:
`$XDG_STATE_HOME/twigpui/reposted_posts.json` で､*このアプリ*が repost した
post の id をすべて保持する｡

**他のクライアント — 公式アプリ､web､ここ以外のどこか — でした repost は
決して反映されない｡** ボタンが示せるのは twigpui 自身がやったことだけで､
スマートフォンから repost した post もここでは "Repost" のままだ｡これは
バグではなく､リクエストコスト 0 で使えるボタンの状態を得るための意図的で
承知のうえのトレードオフだ｡`reposted_posts.json` を失う代償はキャッシュの
エントリを失うより大きい｡失う前に repost したすべての post が再び "Repost"
の表示に戻るので､クリックすると重複を送る恐れがある — それが黙って
間違ったままにならず回復できる理由は､下の「古くなった記録からの回復」を
参照｡

**古くなった記録からの回復｡** ローカルの記録が現実と食い違ったとき —
すでに repost したものを repost する､repost していないものを取り消す —
API は黙って成功するのではなくエラーを返す｡twigpui はその特定の衝突を､
API 自身のエラーテキスト ("already retweeted" / "have not retweeted") に
対する大文字小文字を無視した照合で認識し､失敗として見せるのではなく
ローカルの記録を実態に合わせて直す｡それ以外のエラーはボタンをクリック前の
状態へ巻き戻し､メッセージを表示して再試行を出す｡

**ボタンが付かない post｡** 自分の post には付かない — API が自分自身の
repost を拒否するので､twigpui は必ず失敗するリクエストに金を使う前に
クライアント側で確認する｡repost の行では､この確認は*元の*著者を見る｡
実際に repost されるのはその人の post だからだ｡

**repost の行も操作できる (#52)｡** それ自身が repost である行は元の post の
テキストと著者で描画されるが､その行自身の post id は元の内容のものではなく
retweet のアクティビティのものだ — そしてどの書き込みエンドポイントも元の
post に作用する｡`TimelineItem` は expansion がすでに使っていたのと同じ
`referenced_tweets` の参照から埋めた元の id を持つようになったので､Repost・
Quote・Like のどれもが repost の行で動き､正しい id を送る｡これ以前は
そこで出さずにいたが､それは効いた: ホームタイムラインはほとんどが repost
だからだ｡

## ブラウザで開く

どの post の行にもアプリの外へ出る道が 3 つあり､どれも API リクエストを
消費しない — URL は timeline のレスポンスがすでに運んできたものから
組み立てる:

- byline の行の **"Open in X"** は post 自体を開く
  (`x.com/{handle}/status/{id}`｡著者が展開されなかった post では､X 自身の
  id だけの形 `x.com/i/web/status/{id}` を使う｡行から出る道を無くすのでは
  なく､著者をサーバー側で解決させる)｡
- **著者の名前**はそのプロフィールを開く (`x.com/{handle}`)｡handle が
  展開されなかったときは､指し示せる id だけのフォールバックが無いので
  素のテキストのままにする｡
- **post のテキスト中のリンク**は本文の下にクリックできる行として並ぶ｡

**なぜリンクがテキストの中ではなく下に置かれるか｡** X の post のテキストは
`t.co` の短縮リンクを運んでいて､本当の行き先は `entities.urls[].expanded_url`
からしか得られない — #70 がこれを `tweet.fields` に足したので､すでに支払い
済みのリクエストの中に届く｡リンクを*その場で*クリックできるようにするには
本文をテキストとリンクの要素が交互に並ぶ形へ分割することになるが､gpui は
子をそれぞれ独立したブロックとして配置するので､段落がひとまとまりとして
折り返さなくなる｡各行には X 自身の `display_url` (`example.com/a/b…`) を
ラベルとして付けるので､開くのが展開後の行き先であっても､表示されるものは
テキストが言っているものと一致する｡`expanded_url` を持たないエンティティ
(たとえばメディア添付自身の `t.co`) は､短縮リンクへ戻るリンクとして
見せるのではなく捨てる｡

**開き方｡** `open(1)` は `std::process::Command` を通して直接起動する —
シェルは決して経由しないので､post 由来の URL の中身が構文として読まれる
ことはない — そして渡すのは `http://` と `https://` の URL だけだ｡この
最後の部分は飾りではない: `open` はローカルのパスにも､別のアプリが登録した
スキームにも作用するし､何より先頭の `-` を自分のフラグとして読んでしまう｡
この検査に通らない URL や､起動に失敗したブラウザについては､クリックが黙って
何もしないのではなくバナーを表示する｡

## like と like の取り消し

ほとんどの post に "Like" / "Liked" のトグルが出る｡"Like" のクリックは
`POST /2/users/:id/likes` を送り､(取り消しの) "Liked" のクリックは
`DELETE /2/users/:id/likes/:tweet_id` を送る｡上の repost トグルとまったく
同じ挙動で — クリックで楽観的に切り替え､失敗したら巻き戻し､確認ダイアログは
無い — 仕組みもそれと共有している (`src/toggle.rs`)｡

ローカルな記録について repost の節が言っていることは､`reposted_posts.json`
を `liked_posts.json` に置き換えれば､そのままここにも当てはまる: X API v2 は
「自分がこれを like したか」のフィールドも報告しないし､他のクライアントで
した like は決して反映されないし､古くなった記録は失敗として表に出すのでは
なく API 自身のエラーテキスト ("already liked" / "have not liked") から
直される｡

**repost との違いが 2 つある｡** 自分の post にも Like ボタンは*付く* —
X は自分自身の repost を拒否するが､自分自身への like は受け付ける｡そして
like には `like.write` スコープが要り､X はこれを `tweet.write` とは別に
付与する: #68 より前に認可したセッションは post と repost はできるが like は
できないので､それを直すのがヘッダーの "Re-authorize" ボタン (#14) だ｡
サインインのフローをやり直すとすべてのスコープをまとめて要求する｡
